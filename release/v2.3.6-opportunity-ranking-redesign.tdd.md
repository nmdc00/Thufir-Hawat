# TDD: Opportunity Ranking Redesign — v2.3.6

## Scope

Deliver a concrete replacement for spike-led alerting by introducing:

1. normalized candidate generation,
2. multi-factor opportunity scoring,
3. hard ineligibility floors,
4. ranked shortlist production for originator and discovery,
5. runtime observability proving cross-asset parity.

The release goal is not to remove all heuristics.
It is to stop heuristics from acting as the final opportunity judgment.

## Current Repo Findings

The current runtime already exposes the right seams for this redesign:

- [src/discovery/market_selector.ts](/home/nmcdc/projects/Thufir-Hawat/src/discovery/market_selector.ts)
  - builds the cross-asset discovery set
  - currently ranks mostly for liquidity and execution readiness
- [src/core/ta_surface.ts](/home/nmcdc/projects/Thufir-Hawat/src/core/ta_surface.ts)
  - computes the current activity features
  - currently decides `alertReason`
- [src/core/origination_trigger.ts](/home/nmcdc/projects/Thufir-Hawat/src/core/origination_trigger.ts)
  - currently turns any alert into immediate originator work
- [src/core/llm_trade_originator.ts](/home/nmcdc/projects/Thufir-Hawat/src/core/llm_trade_originator.ts)
  - already consumes a finite candidate context
- [src/core/autonomous.ts](/home/nmcdc/projects/Thufir-Hawat/src/core/autonomous.ts)
  - already has the shared downstream enforcement chain after candidate formation
- [src/core/llm_entry_gate.ts](/home/nmcdc/projects/Thufir-Hawat/src/core/llm_entry_gate.ts)
  - should remain downstream of the new ranking layer, not replaced by it

Therefore:
- the release should introduce a new opportunity-ranking layer,
- it should wire that layer in before originator / discovery candidate choice,
- it should preserve the existing downstream control seam.

Core implementation layers:
- `feature layer`
- `normalization layer`
- `candidate generation layer`
- `component scoring layer`
- `hard-floor eligibility layer`
- `ranking / shortlist layer`
- `observability layer`

Required fields:
- `attentionScore`
- `structuralEdgeScore`

Persistable log record or audit payload.

This can live in a new table or in a structured runtime journal, but the artifact must exist.

## Scoring Contract

### Formula

```text
OpportunityScore =
  0.20 * AttentionScore +
  0.30 * StructuralEdgeScore +
  0.20 * CrowdingQualityScore +
  0.15 * RegimeFitScore +
  0.15 * ExecutionQualityScore
```

### Required Semantics

- `AttentionScore`
  - measures dislocation and attention only
  - must not dominate final ranking by itself
- `StructuralEdgeScore`
  - measures mechanism, payoff, invalidation quality, and relative setup strength
  - highest-weight component
- `CrowdingQualityScore`
  - distinguishes constructive participation from late crowding or exhaustion
- `RegimeFitScore`
  - rewards compatibility between setup family and current regime
- `ExecutionQualityScore`
  - rewards clean tradability and penalizes poor liquidity or vague invalidation

## Normalization Contract

Normalization must prevent raw feature scale from silently favoring one asset class.

Required normalization families:
- symbol-relative volume abnormality
- symbol-relative OI abnormality
- asset-aware funding abnormality
- liquidity normalization by asset class
- spread / execution quality normalization by asset class

Design rule:
- same scoring framework for crypto and `XYZ:`
- different baselines where market structure differs
- no different formula by asset class

## Candidate Generation Rules

The candidate generator replaces the current binary alert role.

It should emit candidates from:
- abnormal volume
- abnormal OI
- abnormal funding where applicable
- abnormal realized move
- event / narrative trigger
- cadence inclusion

Important:
- candidate generation is permissive,
- shortlist selection is selective.

`alertReason` should evolve into `triggerReasons[]`.

## Hard-Floor Eligibility

Before ranking shortlist selection, candidates must be marked ineligible if they fail:
- minimum liquidity
- minimum execution quality
- minimum structural edge
- minimum invalidation clarity
- minimum expected `R`
- portfolio conflict rules
- same-symbol stacking rules unless an explicit override condition exists

Ineligible candidates may still be logged, but they must not consume originator shortlist slots.

## Persistence / Observability

### Schema

Add either:
- a new `opportunity_rank_logs` table, or
- a durable structured scan artifact table if one already exists and is appropriate.

Minimum stored fields:
- scan identifier
- symbol and symbol class
- component scores
- final score
- trigger reasons
- failed floors
- shortlist inclusion flag
- timestamp

### Logs / Runtime Artifacts

Every scan should expose:
- total candidates
- eligible candidates
- top-ranked shortlist
- selected symbol
- reason lower-ranked symbols lost

This is required so we can distinguish:
- “crypto was not generated”
- “crypto was generated but ranked lower”
- “crypto ranked well but failed floors”
- “crypto reached shortlist but lost at originator or gate”

## Acceptance Criteria

`v2.3.6` is complete only when all of the following are true:

1. Current binary alerting has been replaced by candidate generation plus ranking.
2. Every candidate has five bounded component scores and a final `OpportunityScore`.
3. Hard-floor failures are explicit and test-covered.
4. Ranked shortlists are available to originator and discovery paths.
5. Cross-asset normalization is test-covered so crypto and `XYZ:` are compared fairly.
6. Runtime artifacts make it possible to explain why one symbol outranked another.
7. Prompt/context wording no longer implies a crypto-only universe where the runtime is mixed.
