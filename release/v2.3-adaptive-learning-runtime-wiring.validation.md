# Production Validation Plan: Adaptive Learning Runtime Wiring — v2.3

## Purpose

This release must be validated on the deployed SHA in production. Local tests are necessary but not sufficient.

The plan below is designed to prevent a repeat of the current failure mode where:
- tables existed,
- read paths existed,
- broad tests passed,
- but production never exercised the write path or the decision-time effect.

## Validation Contract

We are validating five production invariants:

1. new perp predictions persist `signal_scores`
2. resolved learning events reactivate signal-weight learning
3. full closes materialize policy adjustments
4. future decisions consume active adjustments
5. traces and DB state make the above auditable

## Pre-Deploy Checks

Run on the exact promotion SHA:

```bash
pnpm typecheck
pnpm vitest run
pnpm vitest run tests/core/trade-policy-materialization.test.ts
pnpm vitest run tests/memory/learning-signal-audits.test.ts
pnpm vitest run tests/production/adaptive-learning-runtime-contract.test.ts

```

Required result:
- all commands pass

## Post-Deploy Validation Sequence

Use the production process and DB actually writing runtime state:
- runtime: `/opt/thufir/dist/gateway/index.js`
- db: `~/.thufir/thufir.sqlite`

### Step 1. Confirm deployed runtime identity

```bash
ssh -T nmcdc@77.42.29.26 'cd /opt/thufir && git rev-parse --short HEAD && git branch --show-current'
ssh -T nmcdc@77.42.29.26 'ps -ef | grep -Ei "thufir|node" | grep -v grep'
```

Required result:
- running process points at `/opt/thufir`
- commit matches expected deployment SHA

### Step 2. Confirm new predictions carry signal inputs

Wait for at least one new perp decision after deploy, then run:

```bash
ssh -T nmcdc@77.42.29.26 "sqlite3 -header -column ~/.thufir/thufir.sqlite \"
SELECT id, created_at, market_id, symbol,
       signal_scores IS NOT NULL AS has_signal_scores,
       signal_weights_snapshot IS NOT NULL AS has_signal_weights
FROM predictions
WHERE domain = 'perp'
ORDER BY created_at DESC
LIMIT 20;
\""
```

Required result:
- at least one post-deploy perp prediction has `has_signal_scores = 1`

Failure interpretation:
- if `has_signal_scores = 0` for all post-deploy rows, the weight-learning branch is still unwired upstream

### Step 3. Confirm resolved learning events reactivate updates

After at least one post-deploy resolved trade:

```bash
ssh -T nmcdc@77.42.29.26 "sqlite3 -header -column ~/.thufir/thufir.sqlite \"
SELECT id, resolved_at, signal_scores IS NOT NULL AS has_signal_scores
FROM learning_events
ORDER BY resolved_at DESC
LIMIT 20;

SELECT id, learning_event_id, domain, updated_at
FROM weight_updates
ORDER BY updated_at DESC
LIMIT 20;

SELECT id, learning_event_id, domain, run_id, policy_version, created_at
FROM learning_signal_audits
ORDER BY created_at DESC
LIMIT 20;
\""
```

Required result:
- at least one post-deploy `weight_updates` row exists
- at least one post-deploy `learning_signal_audits` row exists

Failure interpretation:
- `learning_events` without new `weight_updates` or audits means `signal_scores` still did not propagate into `recordLearningEvent(...)`

### Step 4. Confirm full close writes the existing learning surfaces

```bash
ssh -T nmcdc@77.42.29.26 "sqlite3 -header -column ~/.thufir/thufir.sqlite \"
SELECT id, symbol, status, source_trade_id, created_at, closed_at
FROM trade_dossiers
ORDER BY created_at DESC
LIMIT 20;

SELECT id, dossier_id, counterfactual_type, created_at
FROM trade_counterfactuals
ORDER BY created_at DESC
LIMIT 20;

SELECT id, case_type, source_trade_id, source_dossier_id, created_at
FROM learning_cases
WHERE case_type IN ('execution_quality', 'thesis_quality')
ORDER BY created_at DESC
LIMIT 20;

SELECT dossier_id, symbol, signal_class, market_regime, gate_verdict, failure_mode, success_driver, created_at
FROM trade_similarity_features
ORDER BY created_at DESC
LIMIT 20;
\""
```

Required result:
- a post-deploy fully closed trade shows:
  - closed dossier
  - counterfactual rows
  - `execution_quality`
  - paired `thesis_quality`
  - similarity feature row

### Step 5. Confirm policy adjustments materialize

```bash
ssh -T nmcdc@77.42.29.26 "sqlite3 -header -column ~/.thufir/thufir.sqlite \"
```

After a later post-deploy decision:

```bash
SELECT COUNT(*) AS comparable_perp_predictions
```

Expected result:
- `comparable_perp_predictions = 0`
- `learning_examples_count` may remain `0`

Reason:
- this release must not reintroduce synthetic perp comparable contamination

## Release Decision

### Ship

Ship only if all of the following are observed on production:
- post-deploy perp prediction with `signal_scores`
- post-deploy `weight_updates`
- post-deploy `learning_signal_audits`
- post-deploy `trade_policy_adjustments`
- later policy trace with consumed adjustment ids or policy reason codes

### Do Not Ship

Do not claim success if any of the following is missing:
- signal-score persistence
- signal audit writes
- policy adjustment writes
- policy adjustment consumption in later decisions

## Suggested Dashboard Additions

Expose these release-critical metrics:
- latest prediction with `signal_scores`
- latest `weight_updates.updated_at`
- latest `learning_signal_audits.created_at`
- active policy adjustment count
- latest dossier with non-empty `activeAdjustmentIds`

This should become the standing health surface for the adaptive loop.
