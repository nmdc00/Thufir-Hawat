# PRD: Adaptive Learning Runtime Wiring — v2.3

## Problem

The post-`v2.0` learning loop is only half-wired in production.

What production proves today:
- closed perp trades create `trade_dossiers`
- many closed dossiers include `review_payload`
- `trade_counterfactuals` are being written
- `execution_quality` and `thesis_quality` learning cases are being written
- `trade_similarity_features` are being written
- live decision traces already consult retrieval and the LLM entry gate

What production does not prove today:
- learned evidence becomes persistent future trade constraints
- signal-weight learning still updates from recent resolved trades
- learning observability shows before/after signal decisions

Observed production failure modes:
- `trade_policy_adjustments` is empty because no runtime path creates adjustments
- `learning_signal_audits` is empty because recent perp predictions do not persist `signal_scores`
- `weight_updates` and `signal_weights` stopped moving because the update gate requires `signal_scores`
- `learning_examples` is empty because current production traffic is entirely perp and synthetic perp comparables are intentionally excluded

This means Thufir currently learns descriptively but not prescriptively.

## Goal

Ship a production-real adaptive loop where recent closed-trade evidence can deterministically change future pre-execution behavior.

Required end-to-end loop:

```text
open decision
  -> prediction carries signal inputs
  -> close writes dossier/review/counterfactuals/learning cases/features
  -> adaptation materializes bounded policy adjustments
  -> future decision reads active adjustments
  -> adaptive enforcer changes size/leverage/confirmation/reject outcome
  -> observability proves what changed and why
```

## Non-Goals

- Re-enable synthetic perp rows as comparable calibration examples
- Replace deterministic enforcement with free-form LLM policy changes
- Introduce unconstrained online learning on raw PnL alone
- Depend on local test success as a proxy for production correctness

## Product Requirements

### 1. Perp predictions must persist signal inputs

Every perp `createPrediction(...)` call that is intended to feed learning must persist:
- `signal_scores`
- `signal_weights_snapshot` when available
- enough context to reconstruct the decision source family

This is required so a resolved trade can:
- update `signal_weights`
- write `weight_updates`
- write `learning_signal_audits`

### 2. Closed-trade evidence must materialize active policy adjustments

On a full close, the runtime must:
- gather the closed dossier, review, counterfactuals, and derived similarity features
- aggregate recent comparable evidence for the same runtime scope
- derive bounded proposals with `deriveTradePolicyAdjustments(...)`
- persist active rows in `trade_policy_adjustments`
- expire or deactivate stale rows that no longer meet evidence thresholds

### 3. Runtime scopes must match the existing enforcement reader

Adjustment scopes must be written in the exact dimensions the runtime already matches:
- `symbol`
- `direction`
- `strategySource`
- `triggerReason`
- `signalClass`
- `regime`
- `symbolClass`
- `session`

The initial production scope should prioritize:
- `signalClass`
- `triggerReason`
- `symbolClass`
- `regime`

This is the minimum useful scope that balances sample density and decision relevance.

### 4. Adaptive enforcement must become observably real

Future decisions must show policy effects through existing traces:
- `activeAdjustmentIds` non-empty when an adjustment applies
- `policy:size:*`, `policy:leverage:*`, `policy:confirmation:*`, or `policy:cooldown:*` reason codes when triggered
- dossier `policy_trace_payload` must preserve pre/post size or leverage changes

### 5. Production observability must become release-critical

We must be able to answer these questions directly from production:

1. Are recent predictions carrying signal inputs?
2. Are recent closes producing execution/thesis learning cases?
3. Are recent closes materializing policy adjustments?
4. Are future decisions reading and applying those adjustments?
5. Are signal-weight updates and signal audits moving again?

## User Value

After this release, Thufir should be able to do all of the following in production:
- cut size for repeatedly weak setup families
- cap leverage under learned fragile conditions
- require confirmation when past gate interventions added value
- trigger cooldowns for repeated failure modes
- prove, with auditable traces, that a later decision changed because of learned evidence

## Release Contract

The release is only considered shipped if all of the following are true in production:

1. A newly opened perp prediction stores non-null `signal_scores`.
2. A newly closed perp trade writes:
- a closed `trade_dossiers` row
- at least one `trade_counterfactuals` row
- one `execution_quality` learning case
- one paired `thesis_quality` learning case
- one `trade_similarity_features` row
3. At least one close after deploy creates or updates `trade_policy_adjustments`.
4. At least one later decision shows non-empty `activeAdjustmentIds` in its policy trace.
5. At least one post-deploy resolved learning event writes:
- a `weight_updates` row
- a `learning_signal_audits` row

## Risks

- Over-scoping policy adjustments too narrowly can produce zero usable evidence.
- Over-scoping too broadly can overfit weak evidence into global behavior changes.
- Populating `signal_scores` with unstable heuristics can create noisy updates.
- Writing adjustments on every close without idempotent replacement/expiry can accumulate stale policies.
- Testing only write-side tables without proving future decision-time consumption would repeat the current failure mode.

## Acceptance Criteria

- `signal_scores` are present on newly created perp predictions from all active perp entry paths.
- closed perp lifecycles still write the existing dossier/review/counterfactual/learning artifacts.
- policy adjustments are derived and persisted on close using current learning artifacts.
- adaptive decision traces show applied adjustment ids and reason codes on later decisions.
- production validation commands are defined before implementation and must pass on the deployed SHA.
