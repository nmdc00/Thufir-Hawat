# TDD: Live/Paper Lifecycle Resolution Parity — v2.3.8

## Status

Status: implemented

Owner: `release/live-paper-lifecycle-parity`

This is a focused follow-up to the already-shipped live/paper execution parity refactor.

The earlier refactor correctly converged major entrypoints onto the shared `perp_place_order` lifecycle, but fresh runtime-seam parity testing on shipped `main` proved that the post-execution contract is still not fully mode-independent.

This TDD closes that remaining gap.

Implemented on 2026-05-25:

- executed opens now normalize realized fee/order/fill observations from the adapter result first, with live readback only as fallback
- paper executed opens now persist the same realized execution journal surface as live
- full-close prediction resolution now uses one shared round-trip basis:
  - close realized pnl
  - minus close fee
  - minus matched entry fee from the shared journal
- reduce-only learning cases now use that same canonical net figure
- obsolete mode-split close-resolution helpers were removed from `src/core/perp_lifecycle.ts`

## Why This Exists

The product requirement is strict:

- `paper` and `live` must be the same trading system
- reasoning, gating, leverage, exit policy, journaling, and learning must be the same
- the only intentional difference must be where balances and fills come from

At the moment, that statement is still false in one important area:

- post-execution open metadata normalization
- full-close prediction resolution basis
- full-close learning-loop economics

That means a paper round-trip does not yet prove live round-trip behavior at the economic-resolution layer.

## Current Proven Divergences

### 1. Executed open journal metadata is not normalized

Current executed-open parity failure on shipped `main` was:

- `paper` journal writes:
  - `realizedFeeUsd = 0`
  - `realizedFeeToken = null`
  - `realizedFillCount = 0`
  - `realizedOrderId = 0`
- mocked `live` journal writes:
  - `realizedFeeUsd = 0.250125`
  - `realizedFeeToken = 'USDC'`
  - `realizedFillCount = 1`
  - `realizedOrderId = 123`

Root cause:

- `PaperExecutor` returns `feeUsd` and `orderId`, but the shared journaling path does not hydrate paper open observations from the execution result
- the journal depends on `fetchRealizedPerpFee(...)`, which is effectively a live Hyperliquid readback path

Consequence:

- paper and live write different evidence for the same open
- operator analytics and downstream logic cannot rely on a stable realized-fill journal surface

### 2. Full-close prediction resolution uses different economic bases by mode

Current full-close parity failure on shipped `main` was:

- `paper` prediction resolved:
  - `outcome = NO`
  - `resolution_status = resolved_false`
  - `pnl = -1`
  - `closeBasis = paper_executor`
  - `feeUsd = 0.5`
  - `fillCount = 2`
- mocked `live` prediction resolved:
  - `outcome = YES`
  - `resolution_status = resolved_true`
  - `pnl = 9.745`
  - `closeBasis = live_fill_lookup`
  - `feeUsd = 0.255`
  - `fillCount = 1`

Root cause:

- `resolvePerpCloseSummary(...)` branches on mode
- paper aggregates `listPaperPerpFills(...)` across the prediction window, effectively using both open + close fills
- live aggregates `getUserFillsByTime(...)` using the close-order fill set

Consequence:

- the same trade can be labeled a success in live and a failure in paper
- learning and calibration can drift by mode
- policy adjustments can materialize differently by mode

### 3. Full-close learning economics inherit the same skew

The shared lifecycle currently builds reduce-only learning cases from:

- `result.realizedPnlUsd`
- current `realizedFeeUsd`

Prediction resolution, meanwhile, uses `resolvePerpCloseSummary(...)`.

This creates a second-order risk:

- learning-case economics and prediction-resolution economics are not guaranteed to be derived from the same canonical close basis
- even if they coincidentally agree in one mode, the architecture is still unstable

### 4. The divergence is in the shipped runtime seam, not in helper-only code

This is not a unit-test-only discrepancy.

The failing path is the real runtime path:

- input normalization
- limiter
- policy gate
- executor call
- trade journal write
- prediction creation
- exit policy write
- full-close prediction resolution

So this release must be validated at the runtime seam, not merely at helper level.

## Problem Statement

The current refactor solved "same caller path" but not yet "same economic lifecycle contract."

The remaining problem is:

- `paper` and `live` still derive realized execution observations differently
- `paper` and `live` still derive final close truth differently
- the shared learning loop is therefore not yet guaranteed to be mode-independent

## Release Goal

Make post-execution perp lifecycle semantics mode-independent.

After this release:

- open journals must expose the same realized execution fields in both modes
- full-close prediction resolution must use the same economic basis in both modes
- full-close learning cases must use the same economic basis in both modes
- only the source of raw execution data may differ:
  - paper simulation
  - live venue/account readback

## Non-Goals

This release does not:

- redesign leverage selection
- redesign the exit consultant
- redesign the paper fill simulator
- redesign Hyperliquid order submission
- add new trading strategies
- change high-level autonomous trade selection logic

## Release Contract

These invariants must hold on the exact release SHA.

### Invariant 1. Executed open writes a canonical realized-fill journal surface

For both `paper` and `live`, an executed open through `perp_place_order` must write:

- `realizedFeeUsd`
- `realizedFeeToken`
- `realizedFillCount`
- `realizedOrderId`
- `realizedFillTimeMs`

The fields may differ in value, but they may not differ in schema presence or semantic meaning.

### Invariant 2. Blocked path remains mode-independent

Blocked or limiter-rejected opens must continue to write the same blocked journal contract in both modes.

This release must not regress the already-proven blocked path.

### Invariant 3. Full-close prediction resolution uses one canonical economic basis

On full reduce-only close, prediction resolution must be computed from the same semantic basis in both modes.

The canonical basis for this release is:

- `close_leg_realized_pnl_usd`
- minus `close_leg_realized_fee_usd`
- minus `entry_leg_realized_fee_usd` when the matching open journal exists

Rationale:

- it is economically closer to round-trip truth than close-leg-only net
- it is derivable from the shared runtime persistence surface for both modes
- it avoids direct dependence on mode-specific fill aggregation rules

### Invariant 4. Full-close learning-case economics use the same canonical basis

The reduce-only learning case written on full close must use the same net economics used by prediction resolution.

The learning loop cannot use one basis while calibration uses another.

### Invariant 5. The canonical basis is shared-lifecycle derived, not mode-branch derived

The winning implementation must not keep:

- one paper-only close-summary formula
- one live-only close-summary formula

for prediction truth determination.

Mode may affect how raw observations are collected.
Mode must not affect how final truth is computed once observations are normalized.

## Design

### 1. Normalize execution observations at the lifecycle seam

Introduce a shared normalized execution-observation shape inside `tool-executor` for perp lifecycle finalization.

Minimum fields:

- `realizedFeeUsd`
- `realizedFeeToken`
- `realizedFillCount`
- `realizedOrderId`
- `realizedFillTimeMs`
- `realizedPnlUsd`

This does not need to become a public package-wide type if that would create noisy churn, but the lifecycle must operate on an explicit normalized structure rather than raw ad hoc lookups.

### 2. Hydrate normalized open observations from the adapter result first

For `paper`, the execution result already knows:

- `feeUsd`
- `orderId`
- for closes, `realizedPnlUsd`

So the open journal should not depend on a live-style post-hoc venue lookup to learn facts already returned by the executor.

Required behavior:

- start with execution-result fields
- enrich with live fill lookup only when fields are missing or incomplete
- for `paper`, fill canonical defaults such as:
  - `realizedFeeToken = 'USDC'`
  - `realizedFillCount = 1`
  - `realizedOrderId = parsed paper order id when available`

### 3. Canonicalize full-close truth from normalized lifecycle persistence

On full close, derive economic truth from:

- current close observation
- matching entry observation

Preferred source order:

1. current close observation from the executed close result plus normalized enrichment
2. matching open journal entry for the active position / linked prediction
3. fallback lookup only when normalized fields are still missing

The truth computation must not branch to:

- paper aggregate over all fills
- live aggregate over latest venue order

as separate semantic modes.

### 4. Match the open leg using shared lifecycle artifacts

Full-close truth needs the entry fee.

Matching rule:

- use the linked prediction id when available through exit policy
- otherwise fall back to the most recent non-reduce-only executed journal for the symbol that is consistent with the active lifecycle trade

The lookup must be robust enough to survive:

- autonomous path
- tool path
- programmatic path

without depending on mode.

### 5. Reuse the canonical net figure in both prediction resolution and learning cases

Do not compute:

- one `netRealizedPnlUsd` for `recordOutcome(...)`
- another one for `buildPerpExecutionLearningCase(...)`

The canonical close-resolution summary should be built once and then used by:

- prediction resolution
- learning-case persistence
- any future policy-adjustment materialization from the same close

### 6. Keep provenance differences explicit only where necessary

If a provenance field is needed for debugging, it may be added.

But provenance must not affect truth.

Allowed examples:

- `observationSource = 'paper_executor' | 'live_fill_lookup' | 'result_hydrated'`

Not allowed:

- mode-dependent truth formulas

### 7. Delete dead mode-split resolution code once replaced

This TDD explicitly requires dead-code cleanup.

At minimum, the implementation must remove or collapse obsolete logic that exists only to maintain the old mode-split close-resolution behavior.

Examples of acceptable cleanup:

- remove the old semantic branching in `resolvePerpCloseSummary(...)`
- rename helpers whose old names imply mode-specific truth when they now only perform observation collection
- delete fallback-only code paths that are no longer reachable after canonical normalization

## Risks

### Risk 1. Overfitting to mocked live fills

Mitigation:

- keep the parity contract at the shared lifecycle seam
- use normalized semantics rather than Hyperliquid-specific raw payload assumptions

### Risk 2. Breaking prediction resolution for older rows

Mitigation:

- only change the future runtime path
- do not rewrite historical predictions

### Risk 3. Hidden coupling to exit-policy linkage

Mitigation:

- make the open-leg lookup tolerant of missing prediction linkage
- include a robust symbol + non-reduce-only fallback

### Risk 4. Leaving shadow logic behind

Mitigation:

- explicit dead-code cleanup is part of scope
- do not keep both old and new truth formulas in parallel

## Pragmatic Engineer Execution Notes

This work follows the practical pattern:

- reproduce first on the real seam
- define a narrow release contract
- fix one vertical slice at a time
- keep tests proving runtime behavior, not just helpers
- delete obsolete logic once the contract is covered

This is not a place for speculative abstraction.
The winning implementation is the smallest one that makes the runtime seam truthful and provable.
