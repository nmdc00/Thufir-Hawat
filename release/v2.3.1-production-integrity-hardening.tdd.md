# TDD: Production Integrity Hardening — v2.3.1

## Scope

`v2.3.1` is a production integrity patch on top of `v2.3`.

It addresses two live failure modes observed on production on `2026-05-19`:

- `pruneIntel(...)` raises `SQLITE_CONSTRAINT_FOREIGNKEY` when pruning old `intel_items`
- `perp_position_lifecycles` can contain stale/orphaned rows that are later treated as valid active position state

This release includes both:

- the minimal runtime-safe fixes needed to stop the current failures
- the stronger schema-level follow-up so the same classes of failures are harder to reintroduce

## Current Proven Runtime State

Production verification established:

- `src/intel/store.ts` deletes `intel_embeddings` and `intel_items`, but not `intel_hashes`
- `src/memory/schema.sql` defines `intel_hashes.intel_id -> intel_items(id)` with no delete cascade in the legacy shape
- production logs show `uncaughtException SqliteError: FOREIGN KEY constraint failed` inside `pruneIntel`
- `perp_position_lifecycles` contains at least one orphaned row referencing a missing `perp_trades.id`
- `src/memory/perp_trades.ts` reads lifecycle state without proving the parent trade still exists

## Design

### 1. Minimal fix: prune intel safely

`src/intel/store.ts`

`pruneIntel(...)` must:

- gather old `intel_items` ids
- delete dependent `intel_hashes` rows first
- delete dependent `intel_embeddings` rows
- delete the parent `intel_items`
- run the sequence inside a single SQLite transaction

Required result:

- pruning no longer throws on legacy DBs
- pruning remains correct even before schema migrations have run everywhere

### 2. Stronger follow-up: cascade intel dependencies

Schema contract must be upgraded so the DB itself enforces cleanup:

- `intel_hashes.intel_id REFERENCES intel_items(id) ON DELETE CASCADE`
- `intel_embeddings.intel_id REFERENCES intel_items(id) ON DELETE CASCADE`

Migration requirements:

- preserve valid rows
- drop orphaned legacy dependent rows during migration
- remain idempotent on already-migrated DBs

### 3. Minimal fix: refuse stale lifecycle state

`src/memory/perp_trades.ts`

`getActivePerpPositionTradeId(symbol)` must:

- join `perp_position_lifecycles` to `perp_trades`
- return a trade id only when the parent trade exists
- delete the lifecycle row and return `null` when the lifecycle row is orphaned

Required result:

- runtime no longer treats orphaned lifecycle rows as authoritative active positions

### 4. Stronger follow-up: cascade and scrub lifecycle rows

Lifecycle schema contract must be upgraded to:

- `FOREIGN KEY (trade_id) REFERENCES perp_trades(id) ON DELETE CASCADE`

Migration requirements:

- rebuild legacy lifecycle tables that lack cascade delete
- keep valid lifecycle rows
- remove orphaned lifecycle rows during migration

Startup repair requirement:

- any DB opened by current code should self-heal old orphaned lifecycle rows even before runtime reads them

## Test Plan

### Intel pruning

1. `pruneIntel(...)` returns `0` when no rows qualify.
2. `pruneIntel(...)` deletes hashes, embeddings, and items for pruned intel.
3. Opening a legacy DB migrates `intel_hashes` and `intel_embeddings` to cascade-backed schemas.
4. Migration drops orphaned legacy dependent rows and preserves valid ones.
5. After migration, deleting `intel_items` cascades into both dependent tables.

### Perp lifecycle

1. Opening a legacy lifecycle table migrates it to `ON DELETE CASCADE`.
2. Migration drops orphaned lifecycle rows and preserves valid ones.
3. After migration, deleting a parent `perp_trades` row cascades into lifecycle rows.
4. `getActivePerpPositionTradeId(...)` returns `null` and scrubs an orphan lifecycle row even if one is injected after startup.

## Acceptance Criteria

`v2.3.1` is done only when all of the following are true:

- `pruneIntel(...)` no longer depends on undeclared manual cleanup ordering
- intel dependency tables enforce cascade semantics at schema level
- orphaned lifecycle rows are removed at migration/startup time
- lifecycle reads reject and scrub stale rows defensively
- targeted regression tests cover both the minimal runtime fix and the stronger schema follow-up
