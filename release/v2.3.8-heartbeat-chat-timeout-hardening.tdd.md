# TDD: Heartbeat Chat Timeout Hardening — v2.3.8

## Scope

`v2.3.8` is a production hardening patch for the scheduled operator heartbeat path.

It addresses a live failure mode observed on production on `2026-05-26`:

- scheduled heartbeat turns route through the full conversational LLM path
- the primary remote model call can exceed the production `120000ms` LLM timeout
- the generic chat error string is then logged and forwarded as the heartbeat result

This patch is intentionally scoped to the operator heartbeat path in `src/gateway/index.ts`.

It does **not** redesign the position-risk heartbeat service in `src/core/position_heartbeat.ts`, although that service provides useful precedent for bounded LLM behavior.

## Incident Summary

Observed on production server `77.42.29.26`:

- service: `thufir.service`
- process: `/usr/bin/node /opt/thufir/dist/gateway/index.js`
- deployed commit: `559714a8b891eead53bbcde00c27811933bb9992`
- local repo during investigation: `543b56b`

Confirmed failing log entries:

- `2026-05-26 10:12:59 WEST`
  - `Conversation error Error: LLM request (openai/gpt-5.4) timed out after 120000ms`
  - immediately followed by `Heartbeat response summary: Sorry, I encountered an error. Try again or use /help for commands.`
- `2026-05-26 11:03:00 WEST`
  - same error and same heartbeat summary
- `2026-05-26 11:57:58 WEST`
  - same error and same heartbeat summary

The service stayed up for all observed failures. This is not a process crash or systemd restart loop.

## Current Proven Runtime State

Production verification established:

- `thufir.service` is healthy and running continuously.
- server config uses:
  - `agent.provider: openai`
  - `agent.model: gpt-5.4`
  - `agent.useProxy: true`
  - `agent.useResponsesApi: true`
  - `notifications.heartbeat.intervalMinutes: 5`
  - `notifications.heartbeat.suppressLlmDuringActiveChatSeconds: 0`
  - `notifications.proactiveSearch.mode: heartbeat`
  - `agent.useOrchestrator: false`
- `/opt/thufir/.env` sets `THUFIR_LLM_TIMEOUT_MS=120000`
- `llm-mux` health endpoint on `http://localhost:8317/health` returned `status: ok`

This proves the observed `120000ms` timeout is a production environment override, not an unexplained constant.

## Current Code Path

The current scheduled heartbeat path is:

1. `src/gateway/index.ts`
   - `runHeartbeat()` builds `heartbeatPrompt`
   - optional proactive-search summary is appended
   - `primaryAgent.handleMessage('__heartbeat__', prompt)` is invoked
2. `src/core/agent.ts`
   - `handleMessage(...)` logs `Chat from __heartbeat__`
   - `maybeHandleNaturalLanguageTrade(...)` returns `null` for `__heartbeat__`
   - control falls through to `this.conversation.chat(...)`
3. `src/core/conversation.ts`
   - `chat(...)` runs with execution context `{ mode: 'FULL_AGENT', critical: false, reason: 'chat' }`
   - it performs normal conversation-side work:
     - `buildCurrentTimeContext()`
     - `buildLiveAccountSnapshot()` when live mode applies
     - `prepareProactiveRefresh()`
     - `runToolFirstGuard()`
     - `sessions.compactIfNeeded(...)`
     - session history lookup
     - intel/semantic context building
     - planner/context digest generation
     - main `completeWithFallback(...)` call
4. `src/core/llm.ts`
   - `InfraLlmClient.complete(...)` wraps the call in `runWithTimeout(...)`
   - production timeout resolves to `120000ms`
5. `src/core/agent.ts`
   - generic catch logs `Conversation error`
   - generic catch returns `Sorry, I encountered an error. Try again or use /help for commands.`
6. `src/gateway/index.ts`
   - heartbeat summary is logged from that string
   - because the response is not `HEARTBEAT_OK`, it is sent to Telegram

## Root Cause

The root cause is architectural, not incidental:

1. The scheduled heartbeat uses the same conversational entrypoint as a human chat turn.
2. The production heartbeat path is on the non-orchestrator branch, which is context-heavy.
3. Heartbeat runs every 5 minutes and uses a persistent synthetic user id (`__heartbeat__`), so it accumulates normal session history in the session store and chat DB.
4. The generic chat failure handler returns a human-facing apology string, which is invalid for an operator heartbeat contract.
5. The gateway heartbeat layer accepts any non-empty string as a meaningful response and forwards it.

The observed timeout is therefore the product of:

- heavyweight full-chat prompt assembly
- remote `openai/gpt-5.4` latency through `llm-mux`
- a production timeout ceiling of `120000ms`
- missing heartbeat-specific degradation behavior

## Contributing Factors

### 1. Heartbeat is treated as a normal conversation

`src/core/agent.ts` currently contains a heartbeat exclusion only for the natural-language trade shortcut. It does **not** contain a dedicated heartbeat path. The current test suite explicitly codifies this behavior in `tests/core/access-status-routing.test.ts`, which expects heartbeat prompts to be passed through to `conversation.chat(...)`.

That test reflects the current bug, not the desired contract.

### 2. Heartbeat accumulates session history

`SessionStore.getSessionId('__heartbeat__')` normalizes the heartbeat sender into a persistent internal session. `conversation.chat(...)` then:

- appends heartbeat messages to transcript storage
- stores them in `chat_messages`
- includes recent history in future prompts
- may trigger `compactIfNeeded(...)`

This is useful for user conversations but low-value and risky for a scheduler-driven internal control loop.

### 3. Heartbeat can trigger more than one LLM call

On the non-orchestrator branch, heartbeat may incur:

- an `info_digest` summarization call when context exceeds the threshold
- the main conversational completion call
- additional proactive-refresh/trivial-task activity

Even when these do not all fail, they increase latency variance and provider exposure.

### 4. Active-chat suppression is disabled in production

Production sets:

- `notifications.heartbeat.suppressLlmDuringActiveChatSeconds: 0`
- `notifications.proactiveSearch.suppressLlmDuringActiveChatSeconds: 0`

So heartbeat never defers due to active user interaction, even though this control already exists in the product.

### 5. Human-facing error text leaks across an internal control boundary

The string:

- `Sorry, I encountered an error. Try again or use /help for commands.`

is appropriate for interactive chat and inappropriate for:

- scheduler logs
- heartbeat summary contracts
- Telegram operator alerts

This is a contract violation between the generic agent layer and the heartbeat scheduler.

## Non-Goals

`v2.3.8` should not:

- remove the position-risk heartbeat service
- weaken risk-management autonomy for open positions
- globally raise `THUFIR_LLM_TIMEOUT_MS`
- paper over provider stalls by only increasing timeouts
- introduce a second independent heartbeat decision engine with divergent trading logic

## Design Goals

1. Heartbeat must fail closed.
2. Heartbeat must never emit the generic human chat apology.
3. Heartbeat should use bounded, scheduler-appropriate LLM behavior.
4. Heartbeat should avoid building user-chat context when not needed.
5. The minimal incident fix should be shippable independently of larger refactors.

## Design

### 1. Introduce a dedicated heartbeat execution path

Create a heartbeat-specific path rather than routing through generic `handleMessage(...)`.

Recommended shape:

- add `ThufirAgent.handleHeartbeat(prompt, options?)`
- or add `ConversationHandler.runHeartbeat(prompt, options?)`

Required behavioral differences from normal chat:

- no generic chat catch-string
- no user-facing apology text
- bounded timeout passed explicitly to the LLM path
- heartbeat-only normalization at the boundary
- explicit degraded result on failure

This is the primary fix. Without it, the system will continue to leak interactive error semantics into scheduled control traffic.

### 2. Fail closed at the gateway heartbeat boundary

`src/gateway/index.ts` must not treat any non-empty string as a valid actionable heartbeat result.

Required gateway behavior:

- if heartbeat returns `HEARTBEAT_OK`, do nothing
- if heartbeat returns `HEARTBEAT_ACTION: ...`, notify channels
- if heartbeat raises timeout/error, emit a deterministic internal fallback such as:
  - `HEARTBEAT_OK`
  - or `HEARTBEAT_DEGRADED: heartbeat llm timeout`

For the incident hotfix, `HEARTBEAT_OK` is safer than forwarding a misleading apology or partial analysis.

If a degraded variant is introduced, it must be channel-gated so it does not spam operators every 5 minutes.

### 3. Bound the heartbeat LLM call explicitly

Heartbeat should not inherit the generic production `THUFIR_LLM_TIMEOUT_MS=120000`.

Add a heartbeat-specific timeout config on the scheduler-facing config surface:

- `notifications.heartbeat.timeoutMs`

Recommended default:

- `8000` to `15000`

Rationale:

- existing `heartbeat.llmExitConsult.timeoutMs` already defaults to `8000`
- operator heartbeat is a monitoring loop, not a long-form chat surface
- a shorter timeout reduces queue occupation and stale operator output

### 4. Stop persisting heartbeat as normal chat history

The scheduled internal heartbeat should not write into the same transcript/history path as a user conversation.

Required changes:

- do not append heartbeat turns into session transcript history
- do not store heartbeat turns into chat vector memory
- do not let heartbeat trigger session compaction

Optional:

- keep a separate lightweight heartbeat journal if auditability is needed

This removes prompt growth and avoids wasting memory budget on synthetic control-loop chatter.

### 5. Strip the non-essential chat context for heartbeat

Heartbeat should use a narrowly scoped context builder.

Avoid by default:

- user preference context
- semantic chat history
- normal conversation history
- personality injection beyond the core identity/rules needed for safe tool use
- intel prompt expansions that are not necessary for position/risk review

Keep or preserve selectively:

- `HEARTBEAT.md` workspace instructions
- current time
- position/order/book state
- deterministic tool-first snapshots for open positions or watched markets
- proactive summary only if already available and cheap

If no risk trigger or meaningful open-position state exists, the heartbeat path should be able to resolve to `HEARTBEAT_OK` without a heavyweight reasoning pass.

### 6. Preserve normalized action semantics

The existing `normalizeHeartbeatResponse(...)` rule is correct in principle:

- no verified mutating execution => `HEARTBEAT_OK`
- verified mutating execution => `HEARTBEAT_ACTION: ...`

This invariant must survive the refactor.

However, it must be moved into the dedicated heartbeat path and applied before any scheduler notification logic.

### 7. Separate immediate hotfix from structural cleanup

#### Phase A: Incident hotfix

Minimal required changes:

- dedicated heartbeat handler or special-case in agent/gateway
- explicit heartbeat timeout
- gateway fail-closed behavior
- no generic apology forwarding

#### Phase B: Structural cleanup

Follow-up changes:

- no session persistence for heartbeat
- reduced context surface
- explicit heartbeat result type
- optional degraded-state journaling/telemetry

This keeps the urgent production fix small while still addressing the architectural cause.

## Proposed Config Changes

### New

Under `notifications.heartbeat`:

- `timeoutMs: number = 10000`
- `degradedMode: "ok" | "silent" | "notify" = "ok"`
- `storeHistory: boolean = false`
- `includeProactiveSummary: boolean = true`

Interpretation:

- `timeoutMs`
  - upper bound for scheduler heartbeat LLM work
- `degradedMode`
  - `ok`: convert timeout/error to `HEARTBEAT_OK`
  - `silent`: skip output entirely on degradation
  - `notify`: emit a throttled degraded operator message
- `storeHistory`
  - whether internal heartbeat turns are persisted as chat history
- `includeProactiveSummary`
  - whether proactive-search summary is appended to the heartbeat prompt

### Existing Production Config That Should Change

Current production values that increase incident risk:

- `notifications.heartbeat.suppressLlmDuringActiveChatSeconds: 0`
- `notifications.proactiveSearch.suppressLlmDuringActiveChatSeconds: 0`
- global `THUFIR_LLM_TIMEOUT_MS=120000`

For the heartbeat path specifically:

- do not rely on changing the global env timeout alone
- set and honor heartbeat-local timeout/config first

## Validation Strategy

The findings for this incident must be proven with paired control cases rather than only by reading logs.

### Deterministic proof cases

1. Fast control:
   - heartbeat path uses a fake LLM that returns quickly
   - expected result:
     - heartbeat returns `HEARTBEAT_OK` or `HEARTBEAT_ACTION: ...`
     - no degraded path is taken
     - no generic conversation error text appears

2. Timeout case:
   - heartbeat path uses a fake LLM that throws or stalls beyond the configured heartbeat timeout
   - expected result:
     - no `Sorry, I encountered an error...` string is returned
     - heartbeat degrades according to scheduler config
     - gateway delivery behavior follows the degraded contract

3. Routing proof:
   - `__heartbeat__` must no longer rely on the generic chat route by default
   - a regression test must fail if heartbeat falls back to the old generic interactive error surface

4. Persistence proof:
   - when `notifications.heartbeat.storeHistory=false`, heartbeat must not append to normal session transcript/chat memory
   - normal user chat must still persist as before

### Gateway heartbeat behavior

1. Scheduled heartbeat returns `HEARTBEAT_OK` when the dedicated heartbeat path reports no action.
2. Scheduled heartbeat sends channel notifications only for `HEARTBEAT_ACTION: ...`.
3. Scheduled heartbeat does not forward the generic apology string after an LLM timeout.
4. Scheduled heartbeat degrades according to `notifications.heartbeat.degradedMode`.

### Timeout handling

1. Heartbeat-specific timeout uses `notifications.heartbeat.timeoutMs`, not only global `THUFIR_LLM_TIMEOUT_MS`.
2. A heartbeat timeout is logged with heartbeat-specific context.
3. Timeout does not bubble as `Conversation error` from the generic chat catch path.

### Session/history isolation

1. Heartbeat does not append entries to normal session transcript history when `storeHistory=false`.
2. Heartbeat does not write to chat vector memory when `storeHistory=false`.
3. Heartbeat does not trigger `compactIfNeeded(...)`.

### Contract preservation

1. No verified mutating tool execution => heartbeat normalizes to `HEARTBEAT_OK`.
2. Verified mutating tool execution => heartbeat normalizes to `HEARTBEAT_ACTION: ...`.
3. Heartbeat still respects `HEARTBEAT.md` instructions.

### Routing

1. `__heartbeat__` no longer routes through the generic conversation chat entrypoint by default.
2. Existing human chat behavior remains unchanged for normal users.

## Acceptance Criteria

`v2.3.8` is done only when all of the following are true:

- scheduled heartbeat no longer routes through the generic interactive error surface
- heartbeat timeout/error cannot produce `Sorry, I encountered an error. Try again or use /help for commands.`
- heartbeat has its own bounded timeout behavior
- heartbeat defaults to fail-closed behavior on timeout
- heartbeat no longer depends on synthetic accumulated chat history
- tests cover timeout, routing, action normalization, and channel dispatch behavior

## Rollout Notes

Recommended rollout order:

1. ship code-level heartbeat boundary fix
2. set production `notifications.heartbeat.timeoutMs`
3. restore non-zero active-chat suppression windows on production
4. monitor:
   - heartbeat timeout count
   - degraded heartbeat count
   - channel-send rate
   - average heartbeat latency

If production still shows frequent heartbeat degradations after the path is bounded and history-free, the next investigation should focus on upstream `llm-mux` / provider latency rather than the heartbeat contract itself.
