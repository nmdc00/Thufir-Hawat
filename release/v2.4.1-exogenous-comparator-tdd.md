# TDD: Exogenous Perp Comparator and Forecast Target Semantics - v2.4.1

## Status

Status: implemented

Owner: local implementation

Implemented on 2026-06-12:

- Added frozen forecast-target and comparator metadata columns to `predictions`.
- Added `price_climatology` as a deterministic exogenous comparator over supplied OHLCV candles.
- Preserved `segment_history_blended` as an internal baseline and stopped labeling it `market_price`.
- Restricted perp `learning_comparable` creation to exogenous comparator kinds.
- Split dashboard/API prediction accuracy into market-comparable and internal-baseline metric families.
- Added contamination guards so synthetic, missing, and internal comparator rows cannot enter market-proof windows.

This is a focused follow-up to `v2.4-perp-prediction-baselines-prd-tdd.md`.

v2.4 correctly created an automatic baseline path for perp predictions, but the shipped semantics are not yet strong
enough for the product claim "Thufir beats the market baseline." The current generated baseline is
`segment_history_blended`, sourced from Thufir's own historical execution outcomes. That is valid for internal edge
discovery and policy learning, but it is not exogenous market proof.

This TDD fixes the semantic gap without weakening the existing learning loop.

## Current State

The current automatic path is:

```text
perp_place_order
  -> maybeCreatePerpOpenPredictionArtifacts(...)
  -> resolvePerpPredictionBaseline(...)
  -> createPrediction(...)
  -> createLearningCase(caseType='comparable_forecast')
  -> learning_examples view
  -> rolling Brier/model-vs-baseline metrics
```

The important current implementation details are:

- `src/core/perp_prediction_baselines.ts` computes `segment_history_blended` from `learning_cases` where
  `case_type = 'execution_quality'`.
- `src/core/tool-executor.ts` writes generated comparable cases with `comparatorKind: 'market_price'`.
- `learning_examples` admits rows when `model_probability`, `market_probability`, `learning_comparable = 1`, and a
  final outcome are present.

That means the system can automatically learn where Thufir has made money, but the comparator is still internal.

## Problem Statement

There are three defects to close:

1. **Misleading comparator labeling**
   - `segment_history_blended` is currently persisted as `comparatorKind: 'market_price'`.
   - It is not market price or market-implied probability.
   - This can make dashboard and Brier-delta language imply external proof when the row only proves performance
     against Thufir's own historical base rate.

2. **Forecast target mismatch**
   - The current v2.4 target is `positive_net_pnl_before_ttl_or_invalidation`.
   - External markets do not know Thufir's entry, stop, TTL, fees, or invalidation logic.
   - A true exogenous comparator needs a market event target, for example:
     - `price_reaches_directional_threshold_before_horizon`
     - `price_above_level_at_horizon`
     - `barrier_hit_before_horizon`

3. **Comparable-window contamination risk**
   - If internal and exogenous baselines both flow through the same `market_probability` field without source gating,
     rolling Brier deltas can mix two claims:
     - "Thufir beats its own segment-history base rate."
     - "Thufir beats an external market/price-data baseline."
   - Those are both useful, but they must not be collapsed into one headline metric.

## Release Goal

Add a regression-proof exogenous comparator layer for autonomous perp predictions while preserving the existing
internal edge-discovery baseline.

After this release:

- Internal execution-history baselines remain available for policy learning and setup discovery.
- Exogenous price-climatology baselines can be generated at decision time for explicit market-event targets.
- Comparable forecast rows carry source semantics strong enough to separate:
  - internal segment-history comparison
  - price-climatology comparison
  - future options-implied comparison
- Dashboard/API metrics cannot accidentally label internal baselines as market baselines.
- Synthetic `0.5`, missing, stale, or target-mismatched comparators never enter market-proof windows.

## Non-Goals

This release does not:

- Remove `segment_history_blended`.
- Replace execution learning, close learning, suppression, or trade policy materialization.
- Implement CME/options-implied probabilities.
- Backfill old predictions as market-comparable without frozen source metadata.
- Depend on live network calls during tests.
- Require exact probabilistic finance rigor beyond a defensible Tier 1 climatology baseline.

## Vocabulary

### Internal Baseline

An internal baseline is computed from Thufir outcomes.

Current example:

```text
segment_history_blended
```

Use it for:

- automatic edge discovery
- setup suppression
- sizing confidence
- "where has Thufir made money?"

Do not use it for:

- "beats the market" claims
- externally comparable Brier headline metrics

### Exogenous Comparator

An exogenous comparator is computed without Thufir's realized outcomes.

Initial implementation:

```text
price_climatology
```

Future implementation:

```text
options_implied
```

Use it for:

- market-proof Brier deltas
- calibration claims against non-Thufir evidence
- dashboard/YC/customer-facing forecast skill metrics

## Forecast Target Contract

Introduce explicit forecast-target metadata for perp predictions.

Required target fields:

```ts
type ForecastTargetKind =
  | 'positive_net_pnl_before_ttl_or_invalidation'
  | 'price_reaches_directional_threshold_before_horizon';

type PriceClimatologyTarget = {
  kind: 'price_reaches_directional_threshold_before_horizon';
  symbol: string;
  direction: 'up' | 'down';
  thresholdPct: number;
  horizonMinutes: number;
  referencePrice: number;
};
```

Rules:

- `segment_history_blended` may support `positive_net_pnl_before_ttl_or_invalidation`.
- `price_climatology` must only support market-event targets.
- A comparator is admissible only if its target exactly matches the prediction target.
- Target metadata must be frozen at prediction creation time.
- The comparator must store enough metadata to recompute/audit the probability later.

## Price Climatology Comparator

Create a new module:

```text
src/core/perp_exogenous_comparators.ts
```

Primary function:

```ts
export function resolvePriceClimatologyComparator(
  config: ThufirConfig,
  target: PriceClimatologyTarget,
  marketData: PriceClimatologyMarketData,
  now?: Date
): ExogenousComparatorResult
```

Required result:

```ts
type ExogenousComparatorResult = {
  probability: number | null;
  comparable: boolean;
  comparatorKind: 'exogenous_price_climatology';
  source: 'price_climatology' | 'missing';
  sampleCount: number;
  wins: number;
  lookbackDays: number;
  thresholdPct: number;
  horizonMinutes: number;
  referencePrice: number;
  frozenAt: string;
  exclusionReason:
    | null
    | 'missing_market_data'
    | 'insufficient_samples'
    | 'target_mismatch'
    | 'invalid_target';
};
```

Computation:

```text
For each historical rolling window:
  direction = up:
    win if max high within horizon >= reference_open * (1 + thresholdPct)
  direction = down:
    win if min low within horizon <= reference_open * (1 - thresholdPct)

probability = wins / samples
```

Requirements:

- Use only OHLCV/price data.
- Use only data available at decision time.
- Clamp final probability to `[0.01, 0.99]` only after sample calculation.
- Do not use Thufir predictions, fills, PnL, learning cases, or policy outcomes.
- Return non-comparable if sample count is below `minComparableSamples`.

Default config:

```yaml
autonomy:
  exogenousComparators:
    priceClimatology:
      enabled: true
      lookbackDays: 730
      minComparableSamples: 100
      defaultThresholdPct: 0.015
      defaultHorizonMinutes: 1440
```

## Tool Executor Wiring

Update `maybeCreatePerpOpenPredictionArtifacts(...)`:

1. Build and persist an internal target:
   - `positive_net_pnl_before_ttl_or_invalidation`
2. Build and persist a market-event target when enough inputs exist:
   - direction from side
   - threshold from explicit input or config default
   - horizon from explicit input or config default
   - reference price from mark/execution price
3. Resolve comparator priority:
   - explicit auditable comparator, if supplied and target-compatible
   - exogenous `price_climatology`, if target-compatible and comparable
   - internal `segment_history_blended`, for internal learning only
   - missing

Important rule:

```text
learning_comparable = 1 for market-proof metrics only when comparator_kind starts with 'exogenous_'.
```

If the product still needs internal comparable windows, create a separate view/metric namespace rather than reusing
market-proof `learning_examples`.

## Learning Views and Metrics

Split comparable metrics by comparator family.

Add views:

```sql
CREATE VIEW market_comparable_learning_examples AS
SELECT *
FROM learning_examples
WHERE comparator_kind IN ('exogenous_price_climatology', 'exogenous_options_implied');

CREATE VIEW internal_comparable_learning_examples AS
SELECT *
FROM learning_examples
WHERE comparator_kind = 'internal_segment_history';
```

If `learning_examples` cannot include `comparator_kind` without compatibility risk, create a v2 view:

```sql
CREATE VIEW learning_examples_v2 AS ...
```

Dashboard/API must report:

- `predictionAccuracy.marketComparable`
- `predictionAccuracy.internalComparable`
- diagnostics by comparator kind/source/exclusion reason

The current `predictionAccuracy.global` should either:

- become market-comparable only, or
- be renamed to avoid implying external market comparison.

## Dashboard/API Requirements

The dashboard must make these states distinguishable:

- no predictions
- predictions with no final outcomes
- final predictions with only internal baselines
- final predictions with insufficient exogenous samples
- final predictions with market-comparable exogenous baselines

Required labels:

- "Market-comparable forecast accuracy" for exogenous comparator rows.
- "Internal baseline forecast accuracy" for segment-history rows.
- Never call `segment_history_blended` a market baseline.

## Risk Notes

- The biggest product risk is semantic, not mechanical: calling an internal base rate a market comparator would create
  false confidence.
- The biggest implementation risk is mixing comparator families in one rolling metric.
- The biggest data risk is accidental backfill of legacy `0.5` rows into comparable windows.

The regression suite must therefore prove source separation, not just non-null probabilities.
